# 원 구현과 AI-assisted hardening의 구분

이 프로젝트의 핵심 기능은 2024년 교내 Linux 프로젝트에서 구현했습니다. Raspberry Pi
환경 구성, Google Drive 변경 감지, 이미지 슬라이드쇼 생성과 현장 재생 흐름은 당시
팀 프로젝트 결과이며 AI 코딩 에이전트로 만든 코드가 아닙니다.

2026년 공개 저장소를 포트폴리오 관점에서 다시 점검하면서 AI 에이전트를 **구현자보다
리뷰어와 정형 리팩터링 도구**로 사용했습니다. 이 단계에서 찾고 수정한 항목은 다음과
같습니다.

- 정의되지 않은 기본 이미지 상수 때문에 오류 처리 자체가 다시 실패하던 문제
- Flask 업로드 파일명을 그대로 경로에 붙이던 path traversal 위험
- 업로드 완료를 기다리는 루프에 대기 구간이 없어 CPU를 점유하던 문제
- 두 실행 모드에 중복된 이미지 리사이즈·영상 생성 코드
- import 시점에 Google 인증을 수행해 단위 테스트와 도구 재사용을 막던 구조
- 최신 Pillow에서 제거된 `Image.ANTIALIAS` 사용과 의존성 재현 정보 부재

## 제가 수행한 수용 판정

AI 제안은 바로 채택하지 않고 원래 두 실행 모드의 동작을 보존하는지 기준으로 검토했습니다.

1. Google Drive 모드와 Flask 모드가 같은 영상 생성 모듈을 사용하되 배경색 등 기존 차이는
   매개변수로 유지했습니다.
2. 외부 입력은 파일 시스템 경계 전에 정규화하고, 확장자뿐 아니라 실제 이미지 내용을
   검사하며 전체 요청 크기를 제한했습니다.
3. 오류 처리 경로가 원래 예외를 가리지 않도록 fallback 이미지는 선택 설정으로 바꿨습니다.
4. 파일 필터링·리사이즈·업로드 이름 정규화는 자동 테스트로 고정했습니다.
5. CI에서 의존성을 새 환경에 설치한 뒤 린트, 문법 검사와 테스트를 다시 실행하도록 했습니다.

이력서에서 설명하는 AI 활용 방식과 동일하게, 오래된 프로젝트의 공을 AI 사용으로 소급하지
않고 **어느 시점에 무엇을 맡겼고 어떤 조건으로 결과를 수용했는지**를 분리해 기록합니다.
